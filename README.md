# Hybrid RAG Retrieval — BM25 + Dense Embeddings with Rank Fusion

A working retrieval-augmented generation retriever combining sparse (BM25) and dense
(sentence-transformer) search via Reciprocal Rank Fusion, with a lexical reranker on top.
Evaluated on 22 hand-labelled queries over five real institutional documents (~31,000 words).

Every number below is produced by the scripts in `src/`, not asserted — `results/` contains
the committed JSON output from a full run.

---

## Results

Recall@3 and MRR across all 22 labelled queries:

| Retriever | Recall@3 | MRR |
|---|---|---|
| BM25 only | **1.000** | **1.000** |
| Dense only (all-MiniLM-L6-v2) | 0.955 | 0.932 |
| Hybrid (RRF + lexical rerank) | **1.000** | **1.000** |

**On totals the hybrid ties BM25 rather than beating it — the evaluation set is
saturated.** These 22 queries are keyword-heavy and the corpus is small, so lexical search
alone already retrieves the correct document every time and there is no headroom for fusion
to show a gain in the aggregate.

**But the per-query analysis is where the real result is.** On the query *"What transport
options are available for getting to NCI?"*, the dense retriever returned chunks from the
wrong document — it drifted toward the quality assurance handbook, the largest document in
the corpus. BM25 matched the exact terms that actually carry the answer (`transport`,
`Luas`, `Dublin Bus`). Rank fusion recovered the correct chunk at rank 1. That is fusion
doing precisely what it exists to do: the two retrievers fail in uncorrelated ways, so one
covers for the other. An aggregate score cannot surface that; only reading individual
queries can.

**Two evaluation rounds, and the first is instructive.** Before the intended encoder could
be installed, a TF-IDF + random-projection substitute stood in for dense retrieval:

| Round | Retriever | Recall@3 | MRR |
|---|---|---|---|
| 1 — substitute encoder | BM25 | 1.000 | 1.000 |
| 1 — substitute encoder | Dense (TF-IDF + random projection) | 0.864 | 0.758 |
| 1 — substitute encoder | Hybrid | 1.000 | **0.947** |
| 2 — intended encoder | Dense (all-MiniLM-L6-v2) | 0.955 | 0.932 |
| 2 — intended encoder | Hybrid | 1.000 | **1.000** |

In round 1 the hybrid's MRR fell *below* BM25 alone: the weak dense signal actively dragged
correct chunks down during fusion. Rank fusion is only as good as its weakest input — worth
knowing before deploying one.

**Scaling.** Indexes here are in-memory over 260 chunks and answer in ~5 ms, which says
nothing about an institution-wide deployment. Three documented concerns: brute-force cosine
search stops being viable at thousands of chunks (an ANN index such as FAISS becomes
necessary); policy documents change rarely, so a scheduled weekly full re-index beats
real-time updates on cost; and while the lexical reranker is nearly free, a cross-encoder
needs a separate pass per candidate, so batching and a fixed top-K are required to hold
response times.

**What is not claimed.** The transport case suggests the hybrid advantage grows on a larger,
more varied corpus where exact-match retrieval fails more often. That is recorded as a
reasoned expectation, not a demonstrated result — 22 queries cannot establish it.

**Chunking sweep.** Grid search over chunk size / overlap and RRF fusion_k found
chunk_size=150 / overlap=30 optimal (260 chunks). Zero overlap degraded BM25 recall to
0.955, confirming overlap matters at this chunk size.

**One real bug, documented.** An earlier reranker counted raw token overlap including
stopwords, which systematically favoured long generic chunks over the short chunk actually
containing the answer. Fixed by restricting the count to content words — see the docstring
on `lexical_overlap_rerank` in `hybrid_retriever.py`.

## Folder structure

```
nci_rag_poc/
├── data/
│   ├── raw_corpus/          5 real NCI documents (.txt), ~31,000 words total
│   └── eval_queries.py      22 hand-labelled (query, expected_doc_id) pairs
├── src/
│   ├── chunking.py          load + clean + word-chunk the corpus
│   ├── sparse_retriever.py  BM25 (rank_bm25)
│   ├── dense_retriever.py   sentence-transformer embeddings, with a TF-IDF
│   │                        + random-projection fallback if the model can't be downloaded
│   ├── hybrid_retriever.py  RRF fusion + lexical-overlap reranker
│   ├── pipeline.py          end-to-end demo on 6 sample queries
│   ├── evaluate.py          Recall@3 / MRR over the 22-query eval set
│   └── hyperparam_sweep.py  chunk_size/overlap and fusion_k grid search
├── results/                 JSON outputs already generated by the scripts below
└── requirements.txt
```

## Setup

Requires Python 3.9+ **and internet connectivity** — `sentence-transformers`
pulls in PyTorch and downloads the `all-MiniLM-L6-v2` model weights
(~90MB) on first run. This is a required install, not optional: the
results quoted in the report's Data Preparation, Hyperparameter
Optimization and Model Evaluation sections were produced with this
package installed, so it must be present to reproduce those numbers.

```bash
cd nci_rag_poc
pip install -r requirements.txt
```

This installs everything needed: `numpy`, `rank_bm25`, `sentence-transformers`,
and `pdfplumber`. The first run will download the MiniLM model weights, which
takes a minute or two depending on connection speed.

`dense_retriever.py` also contains a network-free TF-IDF + random-projection
fallback that activates automatically only if `sentence-transformers` fails
to import (e.g. it wasn't installed, or there's no internet access). This
exists purely as a robustness safeguard so the code doesn't crash outright
in a restricted environment — it is **not** the intended way to run this
POC, and the numbers it produces are weaker than, and different from, the
ones reported. Every script prints which backend is active so it's always
clear which one produced a given result:

```
Dense backend in use: sentence-transformers (all-MiniLM-L6-v2)   <- expected
Dense backend in use: tfidf-random-projection (fallback, no download)   <- only if install/network failed
```

## Running it — order and what each script produces

Run from the `nci_rag_poc/` folder (or reference `src/<file>.py` from
anywhere — paths inside the scripts are resolved relative to the script's
own location, not the current directory).

1. **`python src/chunking.py`** (optional sanity check)
   Loads and chunks the corpus, prints stats (doc/chunk counts, word
   counts). No files written.

2. **`python src/pipeline.py`**
   End-to-end demo: builds both indexes, runs hybrid retrieval on 6 sample
   queries, prints per-query results and latency.
   Writes `results/retrieval_demo_results.json`.

3. **`python src/evaluate.py`**
   The main evidence script. Runs BM25-only, dense-only, and hybrid
   retrieval over all 22 labelled queries and computes Recall@3 and MRR
   for each. This is what the Model Evaluation section's numbers come from.
   Writes `results/evaluation_results.json`.

4. **`python src/hyperparam_sweep.py`**
   Grid search over chunk_size/overlap (4 configs) and RRF fusion_k
   (3 values at the best chunk config), each scored with the same
   Recall@3/MRR evaluation. This is what the Hyperparameter Optimization
   section's numbers come from. Takes longer than the others since it
   rebuilds the index per configuration.
   Writes `results/hyperparam_sweep_results.json`.

`results/` already contains the JSON outputs from a completed run (with the
real sentence-transformers backend), so you don't have to re-run anything
to see the numbers referenced in the report — the scripts are there so the
numbers can be independently verified.

## Notes for reproduction

- Internet access is required on first run, to download the
  `all-MiniLM-L6-v2` model weights via `sentence-transformers`. No API
  keys are needed. After the first download the model is cached locally
  and subsequent runs work offline.
- The corpus is 5 real NCI documents (registration booklet, admissions
  handbook, library referencing guide, exam results FAQ, student card
  guide), chunked into 260 pieces at chunk_size=150/overlap=30 words
  (the config `hyperparam_sweep.py` confirms is best).
- `hybrid_retriever.py` contains a documented bug-fix (see the docstring
  on `lexical_overlap_rerank`): an earlier version of the reranker counted
  raw token overlap including stopwords, which favoured long generic
  chunks over the short chunk with the correct answer. This is fixed by
  restricting the overlap count to content words.
